# AI Website Agent — Complete Operating Manual

This is the **definitive guide** to using the AI Website Agent end-to-end. It is also the internal contract used by:
- The agent's system prompt (orchestrator/src/planner/system-prompt.ts).
- The plan executor (orchestrator/src/routes/changes.routes.ts).
- The WordPress plugin PHP code (plugin/includes/).
- The frontend dashboard (frontend/).

Read this end-to-end if you are integrating a new LLM provider, fixing an issue, or adding a new tool.

---

## 1. Architecture overview

```
┌──────────────────────┐    HTTPS    ┌──────────────────────────┐
│  Frontend Dashboard  │ ─────────▶  │   AI Orchestrator (Node) │
│  (Next.js :3200)     │ ◀───────── │   (Hono :4100)           │
└──────────────────────┘              │   Tools • SQLite          │
                                     └─────────────┬────────────┘
                                                   │ HTTPS
                                                   ▼
                                      ┌────────────────────────┐
                                      │  WordPress + Plugin      │
                                      │  (REST API :10010)       │
                                      │  Reads/writes _elementor_data
                                      └────────────────────────┘
                                                   ▲
                                                   │ (LLM calls)
                                                   │
                                     ┌──────────────────────────┐
                                     │  LLM Provider (Gemini,     │
                                     │  Anthropic, OpenAI, etc.) │
                                     └──────────────────────────┘
```

Two layers of communication:
1. **Frontend ↔ Orchestrator** over `/api/*` (Hono routes).
2. **Orchestrator ↔ WordPress** over `/wp-json/ai-agent/v1/*` (the plugin's REST API).

The orchestrator decides whether a request is a *read* (run any read-only tool directly) or a *plan* (generate a Change Plan first, then execute on approval).

---

## 2. The two flows

### 2.1 Read flow (no plan)

The frontend sends a question (e.g., "list pages"). The orchestrator:

1. Calls the LLM with system prompt + history.
2. The LLM responds with `tool_calls` (e.g., `list_pages`).
3. The orchestrator executes the read-only tool against WordPress.
4. Returns results to the LLM in a second pass.
5. The LLM generates the final natural-language answer.
6. The frontend displays it.

### 2.2 Plan flow (multi-step writes)

For any non-trivial modification (a new page, adding widgets, etc.), the LLM must NOT execute tools directly. It returns a `Change Plan` JSON. The orchestrator:

1. Stores the plan in `changes` table with status `awaiting_approval`.
2. The frontend shows the plan and asks the user to approve.
3. The user clicks "Approve" → frontend POSTs `/api/changes/:id/approve`.
4. The orchestrator executes operations in order.
5. For each operation, the orchestrator resolves placeholders (see §3).
6. Updates status to `completed` (or `failed`).
7. The frontend re-fetches pending changes.

---

## 3. The Placeholder Protocol (CRITICAL)

When the LLM generates a plan, it does NOT know the actual Elementor IDs (they are generated by the plugin on the fly). To express dependencies, it uses these literal placeholders:

| Placeholder | Meaning | Resolved from |
|-------------|---------|---------------|
| `"{{page_id}}"` | The WordPress post ID of the page just created | `create_page` result |
| `"{{container_id}}"` | The Elementor element ID of the container just created | `add_container` result |

The orchestrator's `resolvePlaceholders` function replaces these in arguments before each tool call. **The LLM must always emit these literal strings** — never `0`, `-1`, `"main-container"`, `"abc"`, etc.

### 3.1 Anti-patterns the LLM must avoid

The LLM has been observed to do the following, which **breaks** the workflow:

| Wrong | Right |
|-------|-------|
| `"page_id": 0` | `"page_id": "{{page_id}}"` |
| `"page_id": 123` | `"page_id": "{{page_id}}"` (the ID is unknown at plan time) |
| `"container_id": "main-container"` | `"container_id": "{{container_id}}"` |
| `"container_id": "abc"` | `"container_id": "{{container_id}}"` |
| `parent_id: "root"` for sub-operations | `parent_id: "{{container_id}}"` for nesting |

### 3.2 Defense in depth

Because the LLM may still hallucinate IDs despite the prompt, the executor has a second stage (`resolveSpecialKeys`) that catches common mistakes:

- `page_id === 0` or `""` → uses the most recent created page.
- `container_id` not matching `/^[a-f0-9]{7}$/` → uses the most recent created container.

If both stages fail, the tool call returns HTTP 500 from the WordPress plugin and the executor marks the operation `failed`.

## 4. Elementor data model

WordPress stores per-page Elementor data in post meta key `_elementor_data` as a JSON-serialized array. Each element has:

```json
{
  "id": "cea8767",          // 7-char hex (our plugin generates this)
  "elType": "container",    // 'container' | 'widget' (or 'section'/'column' in legacy v2)
  "settings": {},           // free-form object
  "elements": []            // nested children (only for containers)
}
```

**Widgets** are also elements with `elType: "widget"` and an extra `widgetType` field:

```json
{
  "id": "b38ad01",
  "elType": "widget",
  "widgetType": "heading",
  "settings": { "title": "¡Hola!", "header_size": "h2" },
  "elements": []
}
```

When Elementor renders, it walks this tree. `_elementor_version` (also stored in post meta) determines which legacy/new formats are valid.

### 4.1 Widget IDs are auto-generated

The plugin's `Elementor_Reader::generate_element_id()` produces a 7-character lowercase hex string. The orchestrator stores the result of each `create_*` tool in a per-plan context map:

```typescript
const context = {
  lastPageId: 14,         // from create_page → result.data.id
  lastContainerId: "cea8767"  // from add_container → result.data.new_element_id
};
```

These are substituted into subsequent tool calls.

## 5. The Plugin REST API

Base URL: `/wp-json/ai-agent/v1/` on the WordPress site.

| Endpoint | Method | Auth | Purpose |
|----------|--------|------|---------|
| `/health` | GET | X-AI-Agent-Key | Server info, Elementor version, widgets available |
| `/pages?search=&status=&per_page=` | GET | yes | List pages |
| `/pages/{id}` | GET | yes | Get one page |
| `/pages` | POST | yes | Create page (title, status, builder) |
| `/pages/{id}` | PATCH | yes | Update page |
| `/pages/{id}/duplicate` | POST | yes | Clone page |
| `/pages/{id}/elementor` | GET | yes | Read Elementor tree |
| `/pages/{id}/elementor/containers` | POST | yes | Append container |
| `/pages/{id}/elementor/widgets` | POST | yes | Append widget to container |
| `/pages/{id}/elementor/widgets/{eid}` | PATCH | yes | Update widget settings |
| `/pages/{id}/elementor/elements/{eid}` | DELETE | yes | Delete element |
| `/pages/{id}/elementor/elements/{eid}/duplicate` | POST | yes | Duplicate element |
| `/pages/{id}/elementor/elements/{eid}/move` | POST | yes | Re-parent |
| `/templates` | GET | yes | List Elementor templates |
| `/templates/{id}` | GET | yes | Get one template |
| `/preview/{id}?device=desktop` | GET | yes | Get preview URL |
| `/design-system` | GET | yes | Colors, fonts, spacing |
| `/audit?page_id=&limit=` | GET | manage_options | Audit log |
| `/changes/{change_id}/rollback` | POST | edit_pages | Rollback |

All responses are wrapped:

```json
{ "success": true, "data": { ... } }
// or
{ "success": false, "error": { "code": "FORBIDDEN", "message": "..." } }
```

The client (`wp-client.ts`) unwraps `data` automatically; only `error` surfaces to higher layers.

## 6. The 24 registered tools (orchestrator side)

See `orchestrator/src/tools/index.ts`. Each tool is published to the LLM via the OpenAI-compatible tool-calling format with a JSON Schema. Categories:

### 6.1 Pages

- `get_page` (read, by id)
- `create_page` (write, requires approval)
- `update_page` (write, requires approval)
- `duplicate_page` (write, requires approval)

### 6.2 Elementor structure

- `analyze_page` (read, returns counts/issues)
- `add_container` (write)
- `add_widget` (write)
- `update_widget` (write)
- `delete_element` (write)
- `duplicate_element` (write)
- `move_element` (write)

### 6.3 Templates
- `list_templates` (read)
- `get_template` (read)
- `use_template` (write, clones a template into a page)

### 6.4 Media
- `search_media` (read)
- `get_media` (read)
- `upload_media` (write)
- `replace_image` (write)

### 6.5 Design system
- `get_design_system` (read)

### 6.6 History
- `get_change_history` (read)

The approval gate is in `src/executor/approval-gate.ts` — it hard-codes which tools require approval and refuses everything else.

## 7. The LLM providers

Configured via `orchestrator/.env`:

```
LLM_PROVIDER=gemini      # or anthropic | openai | ollama | minimax | gemini
LLM_MODEL=gemini-3.6-flash
...
```

Each provider implements `LlmProvider` (`src/llm/provider.ts`) and the factory (`src/llm/factory.ts`) instantiates one. Adding a new provider: drop a `xxx-provider.ts` next to the others.

Gemini uses the **OpenAI-compatible endpoint** at `https://generativelanguage.googleapis.com/v1beta/openai`. We re-use the `openai` SDK and point `baseURL` there. If Gemini changes the URL, edit `src/llm/gemini-provider.ts`.

## 8. How "Plan" execution resolves dependencies

`changes.routes.ts` POST `/:id/approve` walks the operations list in order:

```typescript
for (const op of operations) {
  const withPlaceholders = resolvePlaceholders(op.arguments);  // turn "{{x}}" into context.lastX
  const resolvedArgs    = resolveSpecialKeys(withPlaceholders); // turn 0 or non-hex IDs into context.lastX
  const result          = await executeTool(site, changeId, 'approved', op.tool, resolvedArgs, {...});
  captureContext(op.tool, result);                            // update context
}
```

The executor is **stateful per change**. Plans are dry-run-replace-run over a small in-memory map.

## 9. Known gotchas (what to check first when something breaks)

### "the change shows 'Failed' but I see IDs"

The LLM invented `page_id: 0` or `container_id: "main-container"`. The `resolveSpecialKeys` function should catch 0, but invented strings may still slip through. Verify:

```bash
grep "executed successfully" /tmp/orchestrator.log
```

### "API key not valid" 400 from Gemini

The key in `.env` is wrong. Test directly:

```bash
curl "https://generativelanguage.googleapis.com/v1beta/openai/chat/completions" \
     -H "Authorization: Bearer $GEMINI_API_KEY" \
     -d '{"model":"gemini-3.6-flash","messages":[{"role":"user","content":"hi"}]}' \
     -H 'Content-Type: application/json'
```

### WordPress returns HTML for /wp-json/

`permalinks` are not flushed. Run in Local Site Shell:

```bash
wp rewrite flush
```

### Plugin won't activate

`/var/www/html/wp-content/debug.log` shows PHP fatal. Most common: double namespace (use `use` or `\` prefix in classes that live in a sub-namespace).

|------|---------|-------|

## 11. Adding a new tool — checklist

1. **Plugin side**: add endpoint in `plugin/includes/rest/`. Use the `Validator`, `Permissions`, and template WP REST responses.
2. **Orchestrator side**: add to `orchestrator/src/tools/index.ts` (a `makeRestTool` for simple endpoints, or a custom handler for complex ones).
3. **Classification**: add to `READ_ONLY_TOOLS` or `WRITE_TOOLS` in `src/executor/approval-gate.ts`.
4. **System prompt**: if the tool needs specific arguments the LLM often gets wrong, add a guidance line to `src/planner/system-prompt.ts`.
5. **Tests**: add to `tests/unit/tools.test.ts`.
6. **Documentation**: add to `docs/API.md`.
7. **If multi-step**: verify the tool returns an ID the executor should capture (`add_*` return `data.new_element_id`).

## 12. Coding rules

- **WordPress plugin (PHP)**: PSR-4 autoload, one class per file, snake_case → PascalCase file names, namespaces `AIWebsiteBridge\…`. For multi-namespace references, use `use` imports or `\`-prefixed FQN; **never** rely on relative namespaces, that's where the "double AIWebsiteBridge" bug comes from.
- **Orchestrator (TS)**: ESM (`import`), strict mode, no `any`, structured `WpError`, never `process.exit` inside a request handler.
- **Frontend (Next.js)**: Server Components by default, Client Components with `'use client'` only when stateful.
- **Tests**: PHPUnit for plugin, Vitest for orchestrator, Playwright for E2E.

## Appendix B: Why the original bug appeared

When the user typed "Create a page called Contacto with a heading and a paragraph" the LLM responded with a 4-step plan that **did** include `{{page_id}}` placeholders, and our placeholder resolution worked. The user then re-ran with a similar message; this time the LLM responded with `"page_id": 0`, which fell through the resolver (a regex only matched `{{...}}`). Then a special-keys helper was added to catch the `0` case and IDs that aren't 7-char hex. Both layers exist now.

If you change the LLM provider or model version, the LLM may again try plain numbers. Add a third layer in the executor if it becomes a recurring problem (e.g., network failure followed by a 0 substitution).
